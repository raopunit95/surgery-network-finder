# Surgery Network Finder

**Pincode + surgery + insurer → ranked hospitals → the doctors who operate there.**

A static site. No backend, no API key, no database call at request time. The inventory is a set of
JSON files built from a spreadsheet; the browser does the rest. `git push` is the deployment.

```
pincode  ──►  hospitals matching surgery + insurer  ──►  doctors at the chosen hospital
```

**Live:** https://raopunit95.github.io/surgery-network-finder/

---

## Quick start

```
npm run serve
```

Then open http://localhost:8080. There is nothing to install — no dependencies, no build step.
Opening `index.html` straight off disk will *not* work: browsers block `fetch` on `file://`.

To rebuild the data from a fresh inventory export:

```
npm run refresh
```

To run it on invented data instead of the real network:

```
npm run sample
```

## About the data

`data/` holds a point-in-time snapshot of an Indian cashless-surgery provider network: active
hospitals with coordinates, insurer panels and admission volumes, and their doctors with
specialities and OPD timings. It is generated by the tools in `tools/` and **never hand-edited**.

**Only the fields the UI renders are written out.** The build deliberately drops hospital and
escalation email addresses, internal record identifiers, upstream system IDs and the operational
workflow dates that exist on the source rows. The raw export itself is gitignored and must stay
that way. If you point these tools at your own sheet, the column list is in `tools/config.json`.

Two things this snapshot is not:

- **Not authoritative for cashless eligibility.** Insurer panels change without notice and the desk
  at the hospital is the only reliable answer. The UI says so on every page.
- **Not a live feed.** The header shows the generation date; `data/meta.json` carries the timestamp
  and a data-quality report.

## How it works

### The data is built, not queried

```
data/meta.json          counts, the insurer list, a quality report          ~1 KB    on load
data/surgeries.json     every surgery → the specialities it searches        ~4 KB    on load
data/pincodes/NNN.json  pincode → [lat, lon, district, state]              ~1 KB    on search
data/hospitals.json     the search index: every active hospital            ~30 KB   on search
data/detail/N.json      address, map link and doctors, 25 hospitals a file ~3 KB    on a click
data/taxonomy.json      the full resolved mapping — an audit file          —        never
```

Nothing loads that the current screen does not need. The full journey — load, search, open a
hospital — is about 38 KB over the wire.

`hospitals.json` is rows of values under a `cols` header, with city, state and speciality
dictionaried, and each hospital's insurer panel held as a bitmask over the sorted insurer list. The
insurer names alone used to be more than half the file: 36 names written out once per hospital. The
page reads `cols` to find its columns rather than hard-coding positions.

### Ranking is banded, not sorted

Every result falls into a distance band — 20 / 35 / 50 / 100 / 150 / 250 / 350 / 500 / 650 / 800 /
1,000 / 1,250 / 1,500 km, then everything beyond. Fine near the user, coarse far away, because the
difference between 8 km and 18 km changes what you do and the difference between 1,100 km and
1,300 km does not.

Inside a band, hospitals are ordered by volume and reputation rather than raw distance:

```
score = log₁₀(1 + admissions)  +  0.5 · log₁₀(1 + reviews) · (rating / 5)
```

Log-damped so a 5,000-review hospital does not bury a good one with 200. Rating ties break on review
count, then distance. An unrated hospital sinks rather than floats — unknown is not bad, but it does
not belong at the top either.

**The band is the unit of ordering, and the sort only works inside it.** Four orders are offered:
Recommended, Distance, Rating, Most reviewed. None of them can move a hospital past a band boundary.
A global rating sort once put a 4.9 in Vizianagaram above a 4.6 in Noida for someone searching from
Rajasthan, which is a worse answer however good the hospital is. *Distance decides the shortlist;
the sort decides within it.*

The list is capped at 24, filled band by band from nearest outward, so everything hidden is further
away than everything shown. The counter reads `24 of 140`.

### Nothing nearby is an answer, not an error

Pincode 333515 (Jhunjhunu) has no knee-replacement hospital within 50 km; the nearest is 109.5 km
away in Gurgaon. The page widens the search and says so, with the real distance, before the user
reads a single hospital name. Silently showing a hospital 110 km away is worse than an empty screen.

### Distance

An equirectangular approximation, not haversine. At these ranges the error is well below the ~3.5 km
uncertainty already present in a pincode centroid, and it is far cheaper across hundreds of rows.

## The taxonomy — the part worth understanding

Two vocabularies never agreed. A patient types **Piles**; the inventory says **General Surgery**.
The department is the intermediary, and the whole chain is:

```
surgery ─► primary dept ─► secondary dept ─► speciality ─► hospital ─► doctor
───────    ────────────    ──────────────    ──────────    ────────    ──────
SubDept_Map.tsv            taxonomy.json     Dept_Map.tsv  Inventory.xlsx
(col 2)     (col 4)        ("secondary")     (inverted)    (Speciality)
```

Two of the four links are sheets you own. `tools/taxonomy.json` holds the two judgement calls: which
spellings mean the same thing, and which department may stand in for another.

### The department is a filing category, not a matching key

Fanning out through the department works for the departments that map to one speciality. It fails
for the catch-alls. `Aesthetic` spans Plastic Surgery, Dermatology, Medical Cosmetology and Hair
Transplant — so through the department, `Rhinoplasty` matched hair clinics and `Botox` matched
plastic-surgery wards. `General Medicine` spans eight specialities including General Surgery, so
`Dengue` matched surgical hospitals.

**The fix is the optional 5th column of `SubDept_Map.tsv`, `Specialities`.** Filled in, it
*replaces* the department fan-out for that surgery. Left empty, the department route applies. 45 of
218 rows are filled.

Spelling no longer has to be exact. Every speciality — in the inventory, in `Dept_Map.tsv`, and in
that `Specialities` column — passes through the same canonicaliser, so `Dermataology` and
`Dermatology` both resolve and the site displays the correct one. This used to be a trap: a value
had to reproduce the inventory's typos character for character or it silently matched nothing.

### Secondary departments

Some surgeries are performed by another team. `Proctology` matches no active hospital at all, so
without a secondary department `Piles` returns nothing. Resolution is transitive and cycle-safe.

### It polices itself

- The build warns on any surgery still matching more than 3 specialities through its department.
- Each result card shows **which speciality matched**, so a bad mapping is visible rather than
  silent: if `Rhinoplasty` says it matched on `Hair Transplant`, the row is wrong and anyone can
  see it.
- A `Specialities` value no active hospital lists is reported as a probable typo, not quietly
  narrowed to nothing.
- `data/taxonomy.json` spells out every link, so a wrong answer on the site can be traced to the
  row that caused it without re-running anything.

### A new speciality nobody has mapped

A refresh can introduce a speciality `Dept_Map.tsv` has never seen. Hospitals listing only that
speciality become unreachable by every search — an invisible failure. So the build tries to settle
it, and is deliberately narrow about when it will:

**Applied** — these restate a rule you already wrote, they do not invent one:

| Rule | Example |
|---|---|
| the value is itself a department name | `Gynaecology` → Gynaecology |
| a provider brand in front of a known speciality | `AyurVaid ENT` → ENT |
| one cell naming two known specialities | `Urology & Nephrology` → both |
| differs from a mapped speciality only by a modifier word | `Interventional Nephrology` → Nephrology |

**Suggested, and not used** — anything needing a guess is written to
`incoming/Dept_Map.suggested.tsv` with a confidence score and named by `npm run check`. Those
hospitals stay unreachable until you move a line into `Dept_Map.tsv` yourself.

The modifier rule requires the remaining words to be *identical*, not merely shared. A shared word
is not enough: `Renal Transplant` and `Hair Transplant` share "transplant" and belong nowhere near
each other. The loose version of this rule filed kidney transplants under Aesthetic, so that case is
a test now rather than a comment.

## Insurer names

The source carries roughly 70 spellings of 36 insurers — `SBI`, `SBI General`,
`SBI General Insurance Co. Ltd.`. `tools/insurers.json` maps variants to a canonical name. An
unmapped spelling is **kept and reported**, never dropped: it appears as its own dropdown entry and
`npm run check` names it so the map can be extended. Free-text notes that are not insurers at all
are dropped by an explicit list plus a length ceiling.

## Pincode coordinates

Built once from India Post's 160,092 post offices across 19,441 pincodes. Naive averaging gave a p90
spread of 117 km and p99 of 1,119 km — a pincode spanning two districts pulls its centroid into a
field between them. Median, then 50 km outlier rejection, then re-median removed 10,964 offices
across 22% of pincodes, leaving 3.5 km median and 17.5 km p90 residual error. `npm run pincodes`
regenerates it; it does not need running again.

## Layout

| Path | Role |
|---|---|
| `index.html` · `app.js` · `style.css` | the whole site; `app.js` holds all the logic |
| `data/` | generated. **Never hand-edit.** |
| `incoming/Inventory.xlsx` | the raw export. Gitignored — it carries emails and record IDs. |
| `incoming/SubDept_Map.tsv` | 218 rows: surgery → department (+ optional `Specialities`) |
| `incoming/Dept_Map.tsv` | 57 rows: hospital speciality → department (`A\|B` for multi) |
| `incoming/Dept_Map.suggested.tsv` | generated work queue. Nothing reads it back. |
| `tools/refresh.mjs` | the whole pipeline: read → build → validate → map → write |
| `tools/sources.mjs` | the four inputs: workbook, CSV, Sheets API, sample |
| `tools/xlsx.mjs` | a minimal `.xlsx` reader, so there are still no dependencies |
| `tools/taxonomy.mjs` · `taxonomy.json` | the mapping engine and its two judgement calls |
| `tools/lib.mjs` | records, canonicalisation, the compact writer |
| `tools/check.mjs` | health report on what was built — what needs a human |
| `tools/test-taxonomy.mjs` | unit tests for the mapper, mostly for what it must refuse |
| `tools/test-e2e.mjs` | Chromium walk-through of 5 searches + the 333515 fallback |
| `tools/build-pincodes.mjs` | one-time India Post → shards |

## Commands

```
npm run refresh      read incoming/Inventory.xlsx, rebuild data/, then report
npm run refresh:dry  do all of it, write nothing
npm run sample       rebuild from invented data
npm run check        what needs a human; exits 1 only on search-breaking issues
npm test             unit tests, then a real browser through 5 searches
npm run serve        localhost:8080
```

`npm test` matters more than it looks. The failure this project is prone to reads as
"no hospitals near you" — never as an error — so the e2e run fails on a zero-result search.
Playwright is a dev-only dependency resolved from wherever it is installed; the app itself has none.

## Known limits

- Insurer panels and doctor rosters are as accurate as the source export, and no more.
- A hospital with a blank speciality cell cannot be found by any search; a hospital with a blank
  insurer cell vanishes the moment a user picks an insurer. `npm run check` names both by code.
- 37 surgeries still match more than 3 specialities through Gynaecology or Oncology. Left
  deliberately — a cancer patient plausibly wants any oncology unit — but unreviewed.
- Doctor names are published as they appear in the source. See the `publish:safe` note in DEPLOY.md
  if that should change.
